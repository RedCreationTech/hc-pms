# HC PMS 产品定义

状态: 目标产品设计. 本轮仅开发 Batch 1 项目中心, 是否通过验收以实际测试记录为准. 本文的后续能力不代表已实现.

HC PMS 面向按合同交付设备或工程成果的企业, 把订单项目的负责人, 计划, 交付物, 关口, 执行进度及成本放在同一项目上下文中. 它提供跨系统的项目管理视图和可追溯的管理决策, 现场生产与财务记账仍由相应业务系统负责.

## 产品边界

| 维度 | 设计定义 |
|---|---|
| 项目 | 合同级主项目, 单元/业务单元级子项目. 单机是受控的交付/计划结构节点, 不构成第三级组织项目 |
| 计划 | 主项目计划, 子项目计划, 单机计划; 与阶段, 任务, 里程碑, Gate 分开建模 |
| 过程 | 进度, 偏差, 文档交付, 物料齐套, 问题和风险 |
| 财务 | 概算, 预算, 核算, 决算及变更损失, 均需版本和来源 |
| 协作 | 项目团队, 会议与行动项, 任务责任, 审批及审计 |
| 集成 | CRM, OA, ERP, PLM, MES, SRM, 物流物料系统及 BI 的适配合同 |
| 分析 | 多项目, 单项目, 交付物/齐套, 测试, 成本和经营目标看板 |

订单内的研发交付可由 PMS 跟踪. 研发内部工艺, 实验和研发项目的完整生命周期需要单独的业务设计. 首批不替代 ERP 采购, MES 报工或财务总账.

## 角色与责任

| 角色 | 主要职责 | 关键约束 |
|---|---|---|
| 系统管理员 | 账号, 菜单权限, 配置与运维 | 管理员访问应显式授权并留审计, 不把普通登录等同于全项目可见 |
| PM | 主项目, 团队, 阶段和计划协调 | 写操作同时满足功能权限和项目范围权限 |
| 子项目负责人 | 所分配单元/子项目执行 | 后续节点级范围通过授权关系表达, 不从页面过滤推断权限 |
| 项目成员 | 阅读授权项目, 完成所负责任务 | 不因知道项目 ID 获得权限 |
| 审批人/质量负责人 | 计划发布, Gate, 豁免和变更评审 | 审批决定与提交人身份分开记录 |
| 财务人员 | 财务口径, 成本映射与对账 | 财务查看权限独立于普通项目阅读权限 |
| 集成运维人员 | 映射, 失败处理, 对账和重放 | 不通过重放创建未获批准的业务行为 |
| 业务负责人 | 项目组合决策和受权范围看板 | 看板与明细保持同一授权范围 |

## 技术与交付原则

沿用 `ruoyi_clojure` 的 `ruoyi-template` 基础, 建立独立 `hc-pms`. 后端使用 Kit/Clojure, 前端使用 ClojureScript/Reagent/Ant Design 6. 保留模板已有认证, 权限, 动态菜单和 BPM 能力. 开发使用 SQLite, 生产目标为 MySQL. 两种数据库的迁移与关键查询都要验证.

采用先完成业务闭环再扩展外部连接的批次交付. 每个批次包含持久化, 服务端校验, UI, 权限, 审计和可执行验收. 开发样例只能使用合成信息. 原始内部蓝图及逐页提炼不进入公开仓库.

## Batch 1 范围

- 项目中心的查询, 创建, 编辑和详情. 首批不提供项目删除或归档命令.
- 主节点自动创建并随项目资料更新, 子项目/单机节点新增和查询, 合法父子关系校验. 首批不提供子节点编辑, 删除或迁移.
- 项目成员添加和角色调整, 服务端项目数据隔离, 动态菜单权限. 移除成员的撤销命令留到后续批次.
- 项目状态 `draft -> initiated -> planning`, 合法范围内取消, 状态变更审计.
- 统计当前用户有权访问的项目, 以实际数据形成看板.

`planning -> execution` 在 Batch 1 必须拒绝并返回 HTTP 409. 正式计划基线和 Gate 校验尚未交付, 因而不能让界面提前进入执行状态. 后续状态, URS, 文档, 计划, 费用, 集成和 AI 均属于后续批次设计.

## 成功标准

首批成功以真实操作为准: 用户创建项目后刷新仍可读取, 维护结构和成员, 合法推进到计划阶段, 不在管理员/创建者/负责人/成员授权范围内的用户无法读取或修改项目, 看板没有越权泄漏, 非法状态跃迁明确拒绝, 关键操作有审计. 后续产品成功需要业务量化目标和真实运行数据, 本文不编造收益或工期数字.
