# 工程方案与资源管理系统需求整理

> 来源：`pics/` 目录截图。本文按截图文件命名关系整理需求，用于在当前 RuoYi Clojure 框架上新增三个业务一级菜单：`方案智能编制系统`、`项目信息管理`、`资源管理`。当前 RuoYi 原有 `首页` 必须保留，不得替换。
> 硬性要求：系统页面字段必须与截图保持一致；页面风格尽量贴近截图；实现必须遵守当前项目 Clojure/ClojureScript、Reagent 2、React Hooks、Ant Design 6、re-frame、动态菜单/路由体系。

## 1. 总体目标

在当前 RuoYi 管理后台框架中新增一套面向工程方案编制与资源库管理的业务系统，包含：

1. `方案智能编制系统`：方案工作台，支持新增编制、选择工程类别与方案类型、选择/新建项目、进入补充信息页面并维护方案生成内容。
2. `项目信息管理`：项目基础资料台账，支持项目列表、新建项目、编辑项目、删除/查询等基础管理。
3. `资源管理`：标准规范、向量知识库、结构化知识库、优秀案例库、通用图集库等资源维护。

当前框架已有动态菜单、权限、表格、表单、弹窗、抽屉、上传、分页、登录鉴权等基础能力，应尽量复用现有模式，不另起独立前端框架。

## 2. 当前框架落地约束

### 2.1 前端技术约束

- 使用 `frontend/src/com/ruoyi/rouyi/frontend` 下现有 ClojureScript 结构。
- 路由集中在 `frontend/src/com/ruoyi/rouyi/frontend/router.cljs`。
- 主布局和动态菜单位于 `frontend/src/com/ruoyi/rouyi/frontend/pages/layout.cljs`。
- 页面状态以 `re-frame` 事件、订阅和 `db.cljs` 默认状态为主。
- 局部组件状态必须使用 `hooks/use-state`、`hooks/use-effect` 等 React Hooks，不使用 `reagent/atom` 新写局部状态。
- Ant Design 组件必须通过项目现有 `antd.cljs` 包装使用；缺组件时先在 `antd.cljs` 正确定义。
- `Button :icon` 必须传 React 元素：`(r/as-element [:> XxxOutlined])`，不能传字符串。
- `Dropdown :menu :items :label` 若是 Hiccup 节点，必须用 `r/as-element` 包裹。
- `Drawer` 宽度用 `:size`，避免使用已废弃 `:width`。

### 2.2 后端技术约束

- 继续使用当前 Kit/Integrant/Ring/Reitit/HugSQL/SQLite 风格。
- 新业务建议独立命名空间，避免污染系统管理模块：
  - 方案/项目业务：`com.ruoyi.rouyi.domain.project-*`、`com.ruoyi.rouyi.web.controllers.project-*`。
  - 资源业务：`com.ruoyi.rouyi.domain.resource-*`、`com.ruoyi.rouyi.web.controllers.resource-*`。
- 数据库迁移使用现有迁移机制；新增表需支持本地 SQLite。
- API 返回结构应与现有前端 `api.cljs` 封装一致，列表接口支持 `rows/total` 或现有统一分页结构。
- 涉及文件上传的标准规范、知识库、案例、图集等资源，应复用当前上传/文件管理能力或统一新增文件表。

### 2.3 菜单与路由约束

建议新增路由路径如下，最终菜单应由后端菜单数据驱动：

## 4. 功能需求

## 4.1 一级菜单：方案智能编制系统

### 4.1.1 页面定位

业务首页是工程方案工作台，当前页面标题为 `方案管理`，核心是查看方案列表、发起 `新增编制` 流程、选择项目并补充方案生成信息。

### 4.1.2 方案管理列表

列表页必须按 `pics/1-首页.png` 对齐，当前实现为查询区 + 表格：

- 页面标题：`方案管理`。
- 主操作按钮：`新增编制`。
- 查询字段：`方案名称`、`所属项目`、`方案类型`、`方案级别`、`生成时间`。
- 查询按钮：`重置`、`查询`。
- 表格列：`序号`、`方案名称`、`方案类型`、`所属项目`、`方案级别`、`生成时间`、`编制人`。
- 长方案名称、长项目名称必须换行展示，不得造成页面横向滚动。
- 不显示旧版候选列：`工程名称`、`状态`、`进度`、`更新时间`、`操作`。
- 空数据时保留页面结构和 `新增编制` 入口。

### 4.1.3 新增编制：选工程类别与方案类型

应支持：

- 点击 `新增编制` 后进入全屏流程页。
- 顶部展示工程类别选择：`超危大工程（A类）`、`危大工程（B类）`、`一般工程（C/D类）`。
- 下方展示方案类型卡片，当前为：`顶面工程`、`地面工程`、`墙面工程`。
- `顶面工程`、`地面工程` 为不可用状态，显示 `暂未开放`。
- `墙面工程` 为可用状态，显示 `• 可使用`，点击后进入项目选择。
- 卡片边框、选中态、禁用态、说明文字应尽量贴近截图。

### 4.1.4 新增编制：选择项目

应支持：

- 以弹窗形式展示，弹窗标题为 `选择项目`。
- 支持选择已有项目。
- 项目以卡片形式展示，包含项目名称、方案数量、业态、创建时间、工程性质等摘要信息。
- 支持选中态展示。
- 底部或空状态区域显示 `没有找到合适的项目？` 和 `新建项目` 入口。
- 点击 `新建项目` 打开项目长表单。
- 选择项目后进入 `补充信息` 页面。

### 4.1.5 新增项目长表单

该页面同时出现在 `方案智能编制系统` 的 `新增编制` 流程和项目信息管理新建项目流程中，应复用同一套项目表单组件。

截图显示该表单很长，应按分区实现，当前分区包括：

1. `数据来源`。
2. `项目概况`。
3. `人员组织`。
4. `分包队伍`。

硬性要求：

- 表单字段名称、顺序、必填标识必须按截图实现。
- `数据来源` 的两个上传区必须同一行展示。
- `项目概况` 使用三列布局；若某些字段跨整行，应保持跨整行。
- 面积类字段后缀为 `万㎡`，工期类字段后缀为 `天`。
- 长表单需支持页面内滚动，底部固定或清晰展示 `保存`、`取消` 按钮。
- `新增分包队伍` 应在表单内动态追加分包队伍组，默认无分包队伍。
- `分包队伍` 是最后一个分区，后面不得追加 `系统字段` 等截图外内容。

## 5. 数据模型建议

硬性原则：创建业务表前必须先逐截图整理完整字段清单，并把截图上的每一个业务字段落实到可持久化、可回显的数据映射中。不得先编码再补表；不得以“后续补充”“暂存在前端”“只放备注”等方式遗漏截图字段。

为兼顾当前实现和后续扩展，采用两层要求：

- 复现当前效果时，按本文档标注的现有表字段与 `extra_json` 映射保存，确保页面字段完整保存和回显。
- 后续重建或重构数据库时，建议采用“截图字段显式列 + JSON 扩展字段”的方式，把高频查询和核心截图字段拆成显式列。
- `extra_json` 可用于当前已有表结构下承载截图扩展字段，但必须在本文档写清楚字段映射；不能出现页面字段无持久化映射的情况。
- 页面展示 label 必须与截图一致；数据库字段可以按英文规范命名，但字段映射必须在字段清单中写清楚。
- 所有业务表必须考虑逻辑删除，默认使用当前系统已有风格：`del_flag CHAR(1) DEFAULT '0'`，`'0'` 表示正常，`'2'` 表示删除。
- 所有业务查询默认过滤 `del_flag = '0'`；删除接口默认只更新 `del_flag`，不物理删除业务数据。

### 5.7 附件与图库设计

截图中多个页面都有附件、图片、图纸或图库能力，附件不能只保存在前端状态或只放文件目录，必须同时保存“物理文件 + 数据库元数据”。

#### 5.7.1 文件存储位置

当前系统已有 `/system/file` 文件接口，默认物理目录为项目根目录下 `uploads/`。业务系统应在其基础上做隔离，建议使用：

```text
uploads/business/
  project/              # 项目附件
  solution/             # 方案章节附件
  resource/standard/    # 标准规范附件
  resource/vector-kb/   # 向量知识库文档
  resource/case/        # 优秀案例附件/图片
  resource/atlas/       # 通用图集图片/图纸
```

要求：

- 文件名落盘时必须避免覆盖，建议使用 `业务类型/日期/uuid-原始文件名`。
- 数据库保存原始文件名、存储文件名、相对路径、访问 URL、文件大小、MIME 类型、扩展名、上传人、上传时间。
- 页面只通过接口读取附件列表，不直接拼本地路径。
- 删除业务数据时，默认逻辑删除附件元数据；物理文件可保留，后续由清理任务处理。
- 如后续接对象存储，只需替换 `storage_type`、`storage_path`、`file_url`，页面和业务表不应重构。

## 6. API 设计建议

硬性要求：写接口时必须同步写清楚 request 参数的 `spec` 约束，包括 query/path/body。`response` 的结构不要求写 spec，但接口说明中应保持当前项目统一返回风格，方便前端调用。

接口 spec 建议使用当前 Reitit route data 风格，至少包含：

- `:summary`：接口中文说明。
- `:description`：复杂接口说明业务规则。
- `:parameters`：明确 `:query`、`:path`、`:body` 字段、类型、必填项、枚举值。
- 不要求写 `:responses` spec；如需说明返回值，用自然语言描述即可。
- 文件上传接口明确 `multipart/form-data`、文件字段名、允许类型、大小限制；返回附件元数据结构可在接口说明中描述，不作为 spec 硬性要求。
- 删除接口明确是逻辑删除，接口说明中写清楚更新 `del_flag = '2'`。

每个业务接口开发前必须先完成：字段清单 → migration SQL → SQL 查询 → request 参数 spec → handler/service → 前端 API 调用。顺序不能反过来。

示例 route data 形态：

```clojure
["/business/project"
 ["" {:get  {:summary "项目列表"
              :parameters {:query ProjectListQuery}
              :handler list-projects}
       :post {:summary "新建项目"
              :parameters {:body ProjectCreateBody}
              :handler create-project}}]
 ["/:id" {:get    {:summary "项目详情"
                   :parameters {:path PathId}
                   :handler get-project}
          :put    {:summary "更新项目"
                   :parameters {:path PathId :body ProjectUpdateBody}
                   :handler update-project}
          :delete {:summary "逻辑删除项目"
                   :parameters {:path PathId}
                   :handler delete-project}}]]
```

## 8. AI 开发注意事项

### 8.1 截图字段硬性要求

- 开发前必须对每张截图建立字段清单，字段名逐字核对。
- 不允许因为数据库字段命名不同而改变页面展示 label。
- 不允许删除截图中的字段。
- 截图中的字段必须在 migration SQL 中有明确承载字段；不允许仅放 `extra_json` 代替。
- 不确定字段含义时，先按截图 label 建立字段清单并在 migration 中保留可回显字段，待确认后再优化命名。
- 长表单字段可以分阶段实现 UI，但数据库字段必须一次性覆盖截图字段，避免后续数据迁移返工。
- 字段清单必须标注“截图 label / 数据库字段 / 前端 key / 接口 spec 字段 / 是否必填 / 控件类型”。

### 8.2 ClojureScript/React 注意事项

- 新组件必须使用函数组件 + Hooks，不要写新的 `r/atom` 局部状态。
- 表单数据建议用 `hooks/use-state` 保存草稿，提交时调用 API；跨页状态再进入 re-frame db。
- 动态表格行需使用稳定 ID，不用数组 index 作为最终主键。
- Antd `Select`、`Upload`、`DatePicker` 等复杂组件要在边界处理 `clj->js`/`js->clj`。
- 上传组件返回值要统一转换成后端文件结构。
- Dropdown 菜单项 label 是 Hiccup 时必须 `r/as-element`。
- 新图标先在 require 中引入 Ant Design icon，再通过 `r/as-element` 使用。

### 8.3 后端与数据库注意事项

- 必须先生成并评审对应 migration SQL，才能开始写后端 service/controller 和前端页面编码。
- 新表 migration 要可重复初始化本地 SQLite，且包含截图字段、通用审计字段、`del_flag` 逻辑删除字段。
- HugSQL `.sql` 修改后需要全局重启或 `(user/rr)`，因为 SQL 查询启动时加载。
- 控制器保持薄层，业务逻辑放 domain/service。
- 所有列表接口支持分页、关键词、类型筛选。
- 所有业务删除默认逻辑删除，SQL 使用 `UPDATE ... SET del_flag = '2'`，查询必须过滤 `del_flag = '0'`。
- 删除资源前需考虑附件关联；附件元数据同样逻辑删除，物理文件默认保留。
- 文件上传路径、访问 URL、删除策略要统一，优先复用 `uploads/business/...` 和 `biz_attachment`。
- 方案章节建议保存 JSON，避免频繁 migration 阻塞字段迭代。

### 8.4 菜单/权限注意事项

- 新页面必须同时处理：前端 router、layout page mapping、页面渲染分发、后端菜单种子数据/权限。
- 若菜单来自数据库，新增菜单后需确保管理员角色拥有权限。
- 登录后默认页若改为业务首页，需要同步 `db.cljs`、`events.cljs` 和路由路径。

### 8.5 验证注意事项

- 前端改动后运行 `npx shadow-cljs compile app` 或使用 watch 编译确认。
- 后端改动后运行对应 Clojure 测试或至少通过 nREPL reload 验证 namespace 可加载。
- 页面必须用浏览器打开核对：菜单可见、路由可进入、表格可查、表单可保存、回显无丢字段。
- 每完成一个模块，按截图逐项打勾验收。

### 8.6 接口 request spec 注意事项

- 每个新增接口必须定义 request 参数 spec，禁止裸 handler；response 结构不用写 spec。
- request spec 字段必须与截图字段清单、migration 字段、前端 form key 可追溯对应。
- 列表接口 request spec 必须写清分页参数、查询参数、排序参数。
- 上传接口 request spec 必须写清 `multipart/form-data`、文件字段名、业务类型。
- 逻辑删除接口 spec 必须写明不会物理删除。

## 10. 建议的实现顺序

为了降低风险，建议按如下顺序开发：

1. 菜单/路由骨架。
2. 项目信息管理列表 + 新建项目表单。
3. 方案智能编制系统 `新增编制` 流程复用项目表单。
4. 方案编辑章节。
5. 资源管理各子模块。
6. 统一上传/附件。
7. UI 截图级对齐。

原因：项目表单是首页和项目信息管理共用核心；先完成项目基础能力，可以支撑后续方案和资源引用。

## 11. 待确认问题

开发前建议用户确认：

1. `方案智能编制系统` 作为新的业务一级菜单，当前 RuoYi 默认首页保留。
2. 截图中的所有字段是否需要 100% 入库，还是可将部分低频字段保存在 JSON。
3. 资源文件是否只需本地上传存储，还是需要对象存储/外部文件服务。
4. 向量知识库是否本期只做元数据管理，还是需要真实向量化、检索、问答。
5. 方案最终是否需要导出 Word/PDF；若需要，应提前设计章节数据结构。
6. 是否需要与现有 RuoYi 用户/部门/角色权限联动。
