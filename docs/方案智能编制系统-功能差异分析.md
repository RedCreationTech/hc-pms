# 方案智能编制系统 — 旧系统 vs 新系统 功能差异分析

## 一、系统概述

| 维度 | 旧系统（old_code） | 新系统（当前 src） |
|------|---------------------|---------------------|
| 技术栈 | Java Spring Boot + MyBatis-Plus + Python FastAPI + DeepSeek/豆包 LLM | ClojureKit + ClojureScript(Reagent) |
| AI集成 | 深度集成：Python AI 服务自动逐章生成施工方案 DOCX | **完全未实现** |
| 文件处理 | MinIO OSS + Pandoc + python-docx，支持 DOCX↔HTML 双向转换 | 仅基础文件上传/下载 |
| 数据库 | MySQL 8.0（30+业务表） | SQLite（7个 biz_* 表） |
| 定位 | 生产级系统，AI驱动的施工方案自动编制 | 基础 CRUD 框架，功能骨架已搭建 |

## 三、各模块详细差异分析

### 3.1 方案AI生成（核心功能）

#### 旧系统实现
- **入口**：用户选择方案类型（墙面/地面/顶面/脚手架/混凝土/钢筋/雨季/高坠/吊篮）→ 选择项目 → 补充参数 → 触发生成
- **生成流程**（`GenerateSchemeServiceImpl.schemeGenerate()`）：
  1. 检查并发锁（同一用户只能同时生成一个方案）
  2. 创建方案记录（status=DRAFT），初始化章节状态（`SchemeChapterTemplateFactory`）
  3. 调用 Python AI 服务（HTTP POST，携带项目信息+方案参数+参考案例）
  4. Python 服务逐章生成：
     - 按 JSON 模板递归遍历章节结构
     - 每章根据类型选择三种生成方式之一：
       - `agent`：调用资源库生成器（编制依据、重难点、质量保证等）
       - `docx`：直接插入预制 DOCX 模板（含标记替换 `{$总包单位.项目经理$}`）
       - `llm`：调用 LLM 生成（施工条件气象表、项目管理目标、施工方法等）
  5. 生成过程中通过回调接口更新 Java 端章节进度
  6. 生成完毕后保存 DOCX 到 MinIO，更新方案状态
- **方案模板**：每种方案类型对应一个 JSON 章节模板（如 `wall_construction_chapter_template.json`），定义章节层级和生成策略
- **9种方案类型**：落地式脚手架、钢筋工程、混凝土工程、雨季施工、预防高坠、墙面工程、顶面工程、地面工程、吊篮工程

#### 新系统实现
- **仅创建空记录**：点击"生成方案"后直接在 `biz_solution` 表插入一条 `status="draft"`、`progress=20` 的记录
- **无任何 AI 调用**、无模板、无章节状态追踪、无进度更新

#### 需要实现的功能
1. 方案类型配置（JSON 章节模板定义）
2. 方案生成流程（创建 → 初始化章节 → 调用 AI → 进度追踪 → 完成/失败）
3. Python AI 服务对接或在 Clojure 中重新实现生成逻辑
4. 并发控制（每个用户同时只能生成一个方案）
5. 超时检测和自动失败机制

### 3.2 方案章节管理与生成进度

#### 旧系统实现
- **章节状态表**（`generate_scheme_status`）：每章独立记录 `status`（-1=未开始, 0=生成中, 1=完成, 2=失败）
- **前端轮询**：前端调用 `getGenerateStatus()` 轮询，展示每章生成进度
- **超时检测**：`haveGenerating()` 方法检测超时（默认10分钟无进度则标记失败；单章超时则标记该章失败）
- **回调机制**：Python 每完成一章回调 Java 更新状态

#### 新系统实现
- `biz_solution_section` 表支持章节存储（UPSERT），前端有 `solution-editor` 组件可编辑5个固定章节
- **无生成进度**、**无逐章状态**、**无超时检测**

#### 需要实现
1. 章节状态表（每方案 × 每章节的状态追踪）
2. 生成进度 API（前端轮询）
3. 章节模板配置（按方案类型定义章节列表）
4. 超时检测定时任务

---

### 3.3 方案富文本编辑与版本管理

#### 旧系统实现
- **双模式编辑**：
  - DOCX 模式：python-docx 生成 → MinIO 存储 → 下载编辑 → 重新上传（版本管理）
  - HTML 模式：DOCX→HTML 转换（Pandoc/Python） → 富文本编辑 → HTML→DOCX 导出
- **版本管理**（`generate_scheme_file_manage`）：每次保存创建新版本记录
- **内容管理**（`generate_scheme_content_manage`）：存储 HTML 富文本内容，标记 `is_updated`
- **PandocUtil**：`--embed-resources` 将图片内联为 Base64

#### 新系统实现
- `biz_solution_section` 存储 `content_json`（JSON 格式的表单数据）
- 前端有基础的章节编辑器，但只有 5 个固定 section
- **无 DOCX 生成/解析**、**无版本管理**、**无富文本编辑器**

#### 需要实现
1. DOCX 生成能力（可考虑用 Clojure 的 docx4j 或调用 Python/Pandoc）
2. DOCX↔HTML 转换
3. 版本管理表
4. 富文本编辑器（前端集成 ProseMirror/Tiptap 等）

### 3.4 方案下载/导出

#### 旧系统实现
- `download()`：返回文件 ID 供前端下载 DOCX
- `downloadByHtml()`：HTML→DOCX（调用 Python `convertHtmlToDocx()`） → 流式下载
- `editOrView()`：返回文件 ID 供在线预览/编辑
- `editOrViewHtml()`：返回 HTML 内容供富文本编辑器

#### 新系统实现
- **完全未实现**：无下载/导出 API，无文件转换能力

#### 需要实现
1. DOCX 导出 API
2. HTML→DOCX 转换（后端服务）
3. DOCX 文件下载接口

### 3.5 项目信息管理

#### 旧系统实现
- **20+字段**：项目名称、规模、性质、地址、占地面积、建筑面积、建设/勘察/设计/监理/总承包单位、承包范围、分包工程、质量/安全/科技要求、工期、开工/竣工日期、主功能、省份
- **AI 自动解析**（`GenerateProjectAnalyzeServiceImpl`）：
  1. 上传施工组织设计方案（DOCX）
  2. 发送到 Python AI 解析
  3. AI 提取23个实体字段（Prompt 见 `extract_data_prompt`）
  4. 回调保存解析结果
  5. 轮询解析状态（超时3分钟自动失败）
- **综管系统对接**（`getProjectListByZG()`）：从 `appdev.cscec81.com` 同步项目数据（OAuth + Redis 分布式锁）

#### 新系统实现
- `biz_project` 表：基础字段（名称、代码、地址、参建单位等）
- 扩展字段存储在 `extra_json` 中
- `management_staff` 和 `subcontract_teams` 也存储在 `extra_json`
- **无 AI 解析**、**无外部系统对接**

#### 需要实现
1. 人员信息独立存储（至少分包队伍需要独立表）
2. 设计文件 AI 解析（上传 DOCX → AI 提取项目信息）
3. 解析状态轮询 API
4. 可选：外部项目系统对接

### 3.6 项目人员管理

#### 旧系统实现
- **3个独立表**：
  - `generate_project_contractor_staff`：总承包管理人员（岗位、姓名、职称）
  - `generate_project_decoration_staff`：装饰管理部人员
  - `generate_project_subcontract_staff`：分包单位（队伍名、项目经理、技术负责人、安全负责人）
- **删除重建模式**：更新项目时先物理删除所有旧人员记录，再重新插入

#### 新系统实现
- 所有人员数据存储在 `biz_project.extra_json` 中
- 前端有15个预定义岗位角色的表格编辑器
- 分包队伍有独立的 UI 组件

#### 需要实现
1. 考虑是否拆分为独立表（推荐：至少分包队伍独立）
2. 保存/更新逻辑（删除旧记录+重新插入）

### 3.7 标准规范库

- **去重逻辑**：按 specCode 或 specName 去重，已存在则合并资源关联
- **资源关联**：通过 `generate_resource_relation` 关联方案类型和省份

#### 新系统实现
- `biz_resource` 表（`resource_type="standard"`）
- 基础 CRUD
- **无 Excel 导入**、**无去重逻辑**、**无资源关联表**

#### 需要实现
1. Excel 批量导入功能
2. 去重检查逻辑
3. 资源关联机制（方案类型+省份匹配）

### 3.8 章节级向量知识库

#### 旧系统实现
- **双表**：`exp_chapter_vector`（元数据）+ `exp_chapter_vector_content`（HTML 内容，独立表避免大字段影响查询）
- **批量导入**：上传 DOCX → Pandoc 转 HTML → 存储内容 → 建立资源关联
- **层级管理**：支持一/二/三级标题层级，级联树选择
- **向量检索**：Python AI 生成方案时按章节名+方案类型+省份检索相关知识（`getResourceChapter()`）
- **全文检索**：`knowledgeSearch()` 按关键词搜索章节内容

#### 新系统实现
- `biz_resource` 表（`resource_type="vector-kb"`），有 `vector_status` 字段
- 基础 CRUD
- **无向量检索**、**无内容独立存储**、**无层级管理**、**无全文检索**

#### 需要实现
1. 内容独立存储表（或优化查询性能的方案）
2. 章节层级级联选择器
3. 向量检索能力（可考虑接入向量数据库或用简单全文检索替代）
4. 按方案类型+省份匹配逻辑

### 3.9 结构化知识库（9类经验库）

#### 旧系统实现
- **9个独立表**，每类有专属字段：
  1. `exp_emergency_rescue_procedure`：救援名称、救援程序
  2. `exp_construction_key_difficulty`：难点、分析、应对措施
  3. `exp_emergency_disposal_measure`：风险名称、处置措施
  4. `exp_quality_assurance_measure`：保证项、保证措施
  5. `exp_finished_product_protection`：成品名称、伤害、保护方法/时间/要点
  6. `exp_risk_identification_classification`：施工环节、危险源、事故类型、控制措施、风险等级
  7. `exp_safety_management_measure`：管控措施、主要内容、措施类型
  8. `exp_safety_management_policy`：制度名称、制度内容、制度类型
  9. `exp_emergency_response_procedure`：程序名称、程序内容
- 每类通过 `generate_resource_relation` 关联方案类型和省份
- `ExperienceServiceImpl` 统一处理9类资源的 CRUD + 关联

#### 新系统实现
- 统一使用 `biz_resource` 表 + `category` 字段区分类型
- 前端 `structured-kb` 模式只有 name/content/category/province/remark 5个字段
- **无专属字段**（如风险等级、施工环节、成品保护方法等）

#### 需要实现
1. 至少为以下高价值类型增加专属字段：
   - 施工重难点：难点、分析、应对措施
   - 风险辨识：施工环节、危险源、事故类型、控制措施、风险等级
   - 成品保护：成品名称、伤害类型、保护方法、保护时间、保护要点
2. 或者继续用 `extra_json` 存储扩展字段（需前端动态渲染）

### 3.14 资源关联匹配

#### 旧系统实现
- **`generate_resource_relation` 表**：多态关联表
  - `resource_id`：资源 ID
  - `resource_type`：资源类型（1=标准规范, 2=应急救援, ...）
  - `route_type`：关联类型（1=方案类型, 2=省份）
  - `route_value`：关联值（如 "墙面工程"、"山东省"）
- Python AI 生成方案时：
  - `getResource()`：按方案类型+省份检索标准规范和经验知识
  - `getResourceChapter()`：按章节名+方案类型+省份检索向量知识
  - 未匹配到章节内容时自动降级到通用资源

#### 新系统实现
- **完全未实现**：无关联表，资源和方案之间没有关联关系

#### 需要实现
1. 资源关联表（resource_id + resource_type + route_type + route_value）
2. 关联管理 UI（创建/编辑资源时选择适用的方案类型和省份）
3. 按条件检索资源的 API

### 3.15 生成超时与并发控制

#### 旧系统实现
- **并发锁**：`schemeGenerate()` 开头检查是否有正在生成的方案，防止重复触发
- **超时检测**：`haveGenerating()` 定时检测
  - 方案级别超时（默认10分钟无进度 → 标记整体失败）
  - 章节级别超时（单章长时间无进度 → 标记该章失败）
- **状态机**：方案状态 0(生成中) → 1(完成) / 2(失败)

#### 新系统实现
- **完全未实现**

#### 需要实现
1. 生成中的方案标记（防止重复触发）
2. 超时检测机制（定时任务或首次查询时检测）
3. 状态流转逻辑

### 3.16 综管系统对接

#### 旧系统实现
- `getProjectListByZG()`：从 `appdev.cscec81.com` 获取项目列表
- **OAuth 认证**：通过 `PmTokenUtil` 获取 token
- **Redis 分布式锁**：防止多实例并发获取 token
- **Token 缓存**：Redis 存储 token，TTL 与 token 过期时间一致

## 六、实现优先级建议

### P0 - 核心功能（必须实现）

1. **方案AI生成流程**
   - 方案类型配置（JSON 章节模板）
   - 生成触发 → 章节初始化 → AI调用 → 进度追踪 → 完成/失败
   - 并发控制 + 超时检测

2. **DOCX 生成与导出**
   - python-docx 或 Clojure 调用 Pandoc 生成 DOCX
   - HTML→DOCX 转换
   - 文件下载 API

3. **方案富文本编辑器**
   - 前端集成 Tiptap/ProseMirror
   - DOCX↔HTML 双向转换
   - 版本管理

### P1 - 重要功能

4. **AI 问答对话**
   - LLM 集成（DeepSeek/OpenAI）
   - SSE 流式响应
   - 会话管理

5. **资源关联匹配**
   - 资源关联表
   - 按方案类型+省份检索资源

6. **项目信息 AI 解析**
   - 上传设计文件 → AI 提取项目信息
   - 解析状态轮询

### P2 - 增强功能

7. **相似案例推荐**
   - 文本/向量相似度计算
   - 案例推荐 + 文件下载

8. **向量知识库检索**
   - 向量嵌入 + 相似度搜索
   - 或简化为全文检索

9. **标准规范 Excel 批量导入**

10. **综管系统对接**（如需要）

## 七、技术实现建议

### Clojure 后端
- **LLM 集成**：使用 `clj-http` 调用 OpenAI 兼容 API（DeepSeek/豆包均支持）
- **SSE 流式响应**：Ring/Undertow 支持 SSE，或用 `manifold` 流
- **DOCX 生成**：通过 `ProcessBuilder` 调用 Pandoc，或用 `org.docx4j` Java 库
- **向量检索**：可考虑接入 Milvus/Chroma 或用简单 TF-IDF

### ClojureScript 前端
- **富文本编辑器**：集成 `reagent` + Tiptap（ProseMirror）
- **聊天组件**：EventSource API 接收 SSE
- **进度追踪**：轮询 API + 进度条组件

### Python AI 服务（可选）
- 如需保留原系统的生成逻辑，可部署 Python 服务作为微服务
- Clojure 通过 HTTP 调用 Python 服务
- 或将生成逻辑完全用 Clojure 重写（需要大量 Prompt 工程）
