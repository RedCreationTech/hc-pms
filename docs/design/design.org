* 系统概述

** 项目定位

RuoYi-Clojure 是基于 *Kit 框架* + *Reagent 2* + *Ant Design 6* 构建的
RuoYi 风格全栈管理后台.完整实现了系统管理与日志监控共 18 个 RuoYi-Vue
功能模块,并集成 *BPM 工作流引擎(Flowable 8.0)与办公一体化*(请假,报销,
OA 日历/会议,HRM,CRM,报表),核心功能齐平 RuoYi-Vue / ruoyi-office.

参考原版:RuoYi-Vue v3.9.2(https://gitee.com/y_project/RuoYi-Vue ).
目标对标项目:ruoyi-office(Java/SpringCloud)+ ruoyi-office-vben(Vue3 + Vben Admin,
功能源自芋道 yudao-cloud).全量移植不可行(参考后端 4,257 文件 / 322k 行,
552 张表),本项目只取子集,用当前 Clojure 栈 + 内嵌 Flowable 重实现:

| 决策 | 模块 | 落地策略 |
|------+------+----------|
| 必做 | BPM 审批流 | 内嵌 Flowable 8.0,保留标准 BPMN 2.0 |
| 必做 | OA 协同办公 | Clojure 重写(日程/会议等) |
| 高价值 | HRM 人力资源 | Clojure 重写(员工/考勤/薪资/请假) |
| 高价值 | CRM 客户管理 | Clojure 重写(客户/商机/跟进/合同) |
| 高价值 | 数据报表 | Clojure 重写(统计看板) |
| 不移植 | mall 商城 / iot / pay / mp / member | 与栈不匹配,价值低,明确排除 |

* 系统上下文(C4 Level 1)

系统的外部参与者是两类用户:*管理员*(admin,超级管理员,拥有全部权限)与
*普通用户*(ry,只读/办公角色),均通过 Web 浏览器访问.系统本身对外不暴露
其他服务接口,所有浏览器请求经同一 HTTP 入口进入.

系统的持久化与基础设施依赖:

- *业务数据库*:SQLite(默认)或 MySQL / PostgreSQL,存全部 sys_* 系统表与
  biz_* 业务表.通过环境变量 =JDBC_URL= / =MIGRATION_DIR= 切换.
- *Flowable 引擎库*:独立的 H2 1.4.200 文件数据库(=jdbc:h2:file:./flowable=,
  =FLOWABLE_JDBC_URL= 可覆盖),存引擎自建的 ACT_* 表.
- *内存缓存*:进程内缓存(clojure.core.cache),重启即清空.
- *定时调度*:进程内 Quartz 调度器(cronut),无外部依赖.

* 容器视图(C4 Level 2)

系统由三个容器组成,全部部署在同一 JVM 进程(uberjar 可单 jar 交付),
前端为浏览器内运行的单页应用.

** 容器一:单页前端(ClojureScript)

- 由 shadow-cljs 编译的 SPA:Reagent 2(React 19)+ re-frame + Ant Design 6,
  路由用 bidi.
- 页面位于 =src/cljs/com/ruoyi/frontend/pages/=,API 层为单个
  =api.cljs=(约 177 个 =defn=).
- 开发模式由 shadow-cljs watch 提供增量编译(9630 起监听,被占用自动顺延);
  生产构建 =npx shadow-cljs release app= 输出约 5.4MB,由后端容器伺服.

** 容器二:HTTP 后端(Clojure, Kit)

- Kit/Integrant/Reitit/Ring,Undertow 监听 3000 端口(=PORT= 可覆盖),
  同时伺服前端静态资源(=:static {:resources "public"}=)与 /api/* 接口.
- 五层结构:route → controller → domain service → HugSQL → infra/db.clj.
- nREPL 7000 端口(=NREPL_PORT= 可覆盖)供热重载开发.

** 容器三:Flowable 引擎(嵌入式)

- Flowable 8.0 ProcessEngine 以 Integrant 组件(:app.bpm/engine)内嵌于
  后端 JVM,是项目中*唯一*直接接触流程引擎的地方.
- 独立存储:H2 1.4.200 文件库,默认 URL
  =jdbc:h2:file:./flowable;MODE=MySQL;DB_CLOSE_ON_EXIT=FALSE=,
  由 =FLOWABLE_JDBC_URL= / =FLOWABLE_ASYNC= 环境变量覆盖.
- 引擎状态(流程定义,实例,任务,变量,历史)全在 H2;业务记录(请假单,
  报销单等)在应用库,两边通过 business_key / process_instance_id 关联.
- 前端 BPM 建模器曾评估 bpmn-js(纯前端 JS,经 UMD 外置加载),当前主流程
  设计器为自研 HTML/flex 组件(=bpm_flow_designer.cljs=),BPMN XML ↔
  流程节点树双向转换在后端 =domain/business/bpm_flow.clj= 完成.

* 关键设计决策(ADR)

** ADR-1:BPM 采用内嵌 Flowable 8.0 + 独立 H2 文件库(双轨数据库)

- *背景*:需要为系统引入 ruoyi-office 风格的 BPM 审批流.本栈是
  Clojure(JVM),Flowable 是 Java 库;重写在野 BPM 引擎(22k+ 行)不可行.
- *决策*:同进程内嵌 Flowable 8.0 ProcessEngine(Integrant 组件
  :app.bpm/engine),引擎库为独立的 H2 1.4.200 文件数据库
  (=jdbc:h2:file:./flowable=,=FLOWABLE_JDBC_URL= 可覆盖,生产可切
  MySQL/PostgreSQL 仅改 URL).引擎状态(定义/实例/任务/变量/历史)在
  H2 的 ACT_* 表;业务记录(请假单,报销单等)在应用库的 biz_* 表,
  通过 business_key / process_instance_id 关联.Clojure 只写业务壳:
  =bpm/core.clj= 高层 API(部署/发起/审批/驳回/转办/委派/历史/流程图),
  =bpm/engine.clj= 是唯一直接接触引擎的组件.
- *理由*:Java interop 零成本,保留完整 BPMN 2.0 标准(部署 .bpmn,
  任务引擎,流程实例);双轨让应用库保持 SQLite/MySQL 双兼容,Flowable
  库独立互不污染.可行性 spike 已在 JDK 26 端到端验证(Flowable 7.2.0 /
  8.0.0 均可,推荐 8.0.0;异步执行器可用).
- *后果*:
  - H2 必须锁 1.4.200(Flowable 的 IDENTITY 方言不兼容 H2 2.x).
    该版本有 CVE-2022-23221(RCE,仅当 JDBC URL 可被不可信方控制时触发);
    本项目引擎 URL 由配置硬编码,不受影响;更高安全要求时切外部 MySQL/PG.
  - 流程数据跨两个库,备份/排障需同时关注 H2 文件与应用库.
  - 部署时部署方 BPM 配置(候选人策略,节点配置)以
    <flowable:property name="nodeConfig"> JSON 内嵌 BPMN,不改表结构.

源材料未记录"为何不选 Camunda"的对比论证,此处不做臆测(待确认).

** ADR-2:双数据库兼容(SQLite / MySQL,PostgreSQL 宣称支持)

- *背景*:开发/测试默认 SQLite,生产推荐 MySQL(README 技术栈同时列
  PostgreSQL).
- *决策*:
  - 切换机制:=JDBC_URL= + =MIGRATION_DIR= 两个环境变量;迁移双份,
    =resources/migrations-sqlite/= 与 =resources/migrations/= 必须同步.
  - *每条 SQL 语句之后必须紧跟一行 =--;;=*(Migratus 要求 JDBC 单语句
    执行).漏写不报错--只静默执行第一条且迁移标记已完成,属高危坑.
  - SQL 优先共用语法:=INSTR= 不用 =||=,=LIMIT/OFFSET= 不用 ROWNUM,
    =CURRENT_TIMESTAMP= 不用 =datetime('now')=(后者为 SQLite 独有).
  - 函数名不同时提供 =-mysql= 命名变体,Clojure 层用
    =com.ruoyi.infra.db/detect-db-type= 选择(如 last-insert-id /
    insert-and-get-id!).
  - DDL 差异:SQLite =INTEGER PRIMARY KEY= vs MySQL
    =BIGINT AUTO_INCREMENT PRIMARY KEY=;字符串 SQLite TEXT vs MySQL
    VARCHAR(255);时间字段 TIMESTAMP DEFAULT CURRENT_TIMESTAMP;
    幂等插入 INSERT OR IGNORE vs INSERT IGNORE.
  - HugSQL :v* 展开空数组会生成 =IN ()= 语法错误,空集合传 =[0]= 哨兵.
- *后果*:任何新表/新查询必须在两个库各跑一遍全量测试;改完 .sql 必须
  =(user/rr)= 重启系统(HugSQL 查询启动时缓存).

** ADR-3:RBAC + 数据权限

- *背景*:RuoYi 风格管理后台需要用户/角色/菜单三级授权与部门级数据隔离.
- *决策*:
  - 模型:=用户 ── N:N ── 角色 ── N:N ── 菜单(含 perms 按钮权限标识)=,
    用户另属部门(树形).
  - 数据权限范围四种:全部 / 自定义(指定部门)/ 本部门 / 本部门及以下,
    存于角色;运行时由 =infra/data_perm.clj= 的 =apply-data-scope= 过滤.
  - 菜单/按钮权限动态下发:菜单种子迁移插入 sys_menu(目录/菜单 'C'/按钮 'F'
    三级)+ sys_role_menu 授权;登录后 getInfo 返回 perms 集合,前端据
    此渲染菜单和按钮显隐,*不可在前端写死*.
  - 管理类端点沿 =wrap-jwt-auth= + perms 检查;业务路由当前主要靠前端按
    perms 控制按钮显隐(require-perms 已有实现,业务路由未强制使用).
- *后果*:新增模块必须附带菜单种子迁移;权限改动需同时更新 sys_menu 与
  sys_role_menu.

** ADR-4:单一 api.cljs 前端 API 层

- *背景*:前端约 30+ 页面,BPM/OA/HRM/CRM 等业务模块,需要统一的 HTTP 出口.
- *决策*:全部 API 调用集中在 =src/cljs/com/ruoyi/frontend/api.cljs=(单个
  文件,约 177 个 =defn=),按模块分区追加,签名统一
  =[params on-success on-error]=;私有 =request= 函数自动从 re-frame app-db
  取 token 加 Bearer 头.
- *理由*:源材料未记录拆分与否的论证(待确认).现状优点是所有请求的
  认证/错误处理一处实现;代价是文件随模块增长变大,尚无按模块拆分的
  api/ 目录.
- *后果*:新模块按既有分区惯例追加 API 函数;事件层(events.cljs)通过
  reg-fx 调 api 函数,回调里 dispatch set-list.

** ADR-5:cronut 调度(任务存库轮询)与 Quartz 的关系

- *背景*:需要 RuoYi 风格的定时任务管理(CRUD,暂停/恢复/立即执行,
  执行日志).
- *决策*:调度底座是 Quartz 2.3.2,经 kit-quartz 的 cronut 组件接入
  Integrant(:cronut/scheduler).但 =:schedule []= 为空--cronut 只提供
  触发机制,*任务定义存数据库*(sys_job),由 =app.system/job-scheduler=
  组件轮询任务表驱动 Quartz.
- *理由*:与 RuoYi 的"任务存库,运行时管理"语义对齐--任务 CRUD 改库即可
  生效,无需改代码或重启;cronut 的声明式 :schedule 不适合动态任务集.
- *后果*:调度元数据在应用库;调度执行目标函数位于 =com.ruoyi.task=.

** ADR-6:统一接口契约(分页 page/size,响应 {:code :msg :data})

- *背景*:前后端契约需与 RuoYi-Vue 对齐并全项目一致.
- *决策*:
  - 分页参数:前端传 =page= / =size=(*不是* pageNum/pageSize);SQL 层用
    =LIMIT :page_size OFFSET :offset=,领域服务负责换算,列表查询固定配
    一个 =xxx-count=.
  - 响应格式:成功 ={:code 200 :msg "操作成功" :data ...}=;列表
    =data= 为 ={:rows [...] :total N}=.
  - 可选过滤模式 =(:name IS NULL OR INSTR(name, :name) > 0)=,参数为 nil
    时条件自动失效.
  - 更新部分字段用 =COALESCE(:col, col)= 保护未传参的列.
- *后果*:控制器用 =bu/kquery= 把 HTTP 层 string key 的 query-params 转
  keyword key(漏掉则分页/过滤静默失效);前端按 =(:code r)= 判断.
